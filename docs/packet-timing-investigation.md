# Moonlight：自然网络时序诊断与候选方案（2026-11-05）

当前工作假设：**周期性的无线/驱动接收空窗，与播放截止期跟踪不足叠加**。
AWDL 是优先怀疑对象；具体 iOS 实现及无线空口行为仍未直接观测。
这一轮只读分析已有日志和随后上传的新数据，没有制造丢包、重连、改网络或实机参数。
用户确认当前 iPad 正常有声。平台对照不作为本轮证据。

## R1：对照发送、接收与播放，拆开“PLC”和“丢包”

目的：确定失败主要来自未到达、到达过晚，还是输出设备不推进。

方法：关联已有主机 `/tmp/audio_redundancy.log` 的发送尝试元数据与 iPad 逐包记录。
以序号和短时间范围匹配，不把两台机器的墙上时钟视为同步；本次墙上时钟存在约
45 秒偏差。发送时间位于原包 send syscall 之前，也没有 syscall 成功返回值。

结果：

| 指标 | 较早约 299 秒记录 | 随后约 802 秒记录 |
| --- | ---: | ---: |
| 发送序号时间 / 主机经过时间 | 283.880 / 299.412 秒 | 798.560 / 802.031 秒 |
| 实际记录 PLC | 9,973 | 11,120 |
| PLC 对应首个副本后来才到 | 9,776 | 11,025 |
| PLC 对应没有接收记录 | 125 | 90 |
| 日志批次缺口 | 0 | 0 |

“没有接收记录”还包含采集丢记录、裁剪边界等因素，不能直接认定为无线丢包。
首个副本后来到达也不能证明原包丢失：原包可能被缓冲，接收线程也可能晚获调度。
较早记录包含上一轮输出暂停及日志接收端暂停测试；这些没有塑造 UDP 丢包 pattern，
但也不作为完全未干预的听感实验。后面 R3 使用参数冻结后新上传的纯观察窗口。

结论：大量 PLC 对应的是迟到/时间线失配，而非从未出现的数据。
主机送出序号的节奏也会偏离“每帧固定 5ms”，需要和无线空窗分开处理。

## R2：周期结构与可反驳的 AWDL 假设

目的：判断当前影响是否接近独立随机丢包，还是有重复的调度窗口。

方法：按主机原包发送时刻，把接收端首个副本相对最小观测时差晚至少 60ms 的情况分箱。
这个“相对时差”没有去除未知单向路径、主机发送等待及两端频率误差，不是绝对单向延迟。
60ms 门限把此次约 120ms 的延后副本群与快速首副本群区分；它不识别副本的真实身份。

结果：两段历史数据的 10ms 分箱自相关峰均在 520–530ms，520ms 处约为 0.94；
400ms 处为负相关。连续受影响的序号段以 80–100ms 为主。
较早样本拟合周期约 524.492ms，之后五分钟的自相关峰仍在 520–530ms，约 0.937。

[Stute 等的 AWDL 逆向论文](https://arxiv.org/pdf/1808.03156)在第 6.2–6.3、7.4 节记录：
AW 为 16TU，1TU 为 1024µs，通道序列为 64AW，即 1048.576ms；一些管理帧集中在
通道序列两半的开头。**半序列 524.288ms 与本次周期接近，是推断 AWDL 的理由，
不是当前 iOS 的实测协议参数。** 该研究基于早期实现。

可反驳的工作假设：

| 假设 | 预测 / 现有证据 | 仍可竞争的解释 |
| --- | --- | --- |
| H1：AWDL 离频/可用窗口使原包延后或未收到，120ms 副本跨过窗口 | 周期接近历史半序列；受影响段约 80–100ms；副本延后约 120ms | 其他无线省电/驱动调度也可能产生周期 |
| H2：主机的副本发送线程周期性迟到 | 应能在主机 DUP wake delay 看到几十毫秒停顿 | 新窗口 61,389 条记录中 p99=216µs、最大 645µs，不支持其为 80–100ms 空窗的主因 |
| H3：整个 Moonlight 进程周期性停顿 | 网络接收与音频播放应同时停顿 | 新窗口 312 次音视频接收同时静默超过 40ms时，音频播放仍达到正常期望速率的至少 75% |
| H4：接收线程/驱动调度或 AP 缓冲 | 用户态 recv 时刻晚，其他工作线程仍能运行 | 现有时间戳无法区分内核到达与用户态取包；仍然成立 |
| H5：发送前音频队列丢弃或采集停顿压缩 RTP 时间线 | 主机墙上时间前进但序号时间不足 | 已看到这种节奏差；尚无队列溢出计数证明具体路径 |

固定相位预测没有完全通过：用旧样本拟合周期直接预测新窗口，相位分箱曲线相关仅
0.423；事后允许圆周平移，最大约 0.738。不能把后者当作预先预测成功。
**当前适合按空窗长度/副本到达分布设计恢复，不适合写死绝对周期相位。**

关于 H5，本机 Sunshine 源码的 PCM 队列容量 30、编码后 mail 队列通常容量 32；
`queue_t::raise()` 在默认溢出策略下会清空队列，而 RTP 序号/时间戳在稍后的发送阶段推进。
因此理论上存在“发送前丢音频却没有 RTP 序号缺口”的路径。仅有源码路径不证明运行中的
二进制发生了该事件；本轮没有改动或重启 Sunshine。

## R3：冻结候选后，用随后上传的五分钟记录比较

目的：评估扩大缓冲与改进时间线跟踪的作用和代价。

方法：在生产 `AudioBurstGuard` 源码旁构建独立离线重放器，重建不含媒体的 RTP 占位包。
使用真实 ingest 时刻，各策略按自己的截止期调度理想解码工作线程；复用实录 wakeup
会错误限制新策略，因此不这样重放。没有 Opus 解码、FEC 内容、真实 CoreAudio 或听感。
额外用 20ms 起播、250ms 上限的虚拟 PCM 队列估算欠载；这些不是实际扬声器测量。

候选仅在重放器中存在：对首见且向前推进的序号，连同已迟到的数据，取一秒内最小
到达相位误差；正向修正每窗口最多 100ms，负向仍最多 1ms。生产实现的正向修正仅
1ms/秒，且已经判迟到的数据不参与估计。候选测试前已记录代码 SHA256 和日志批次边界；
后续没有调整候选参数。

新观察窗口：原会话批次 790–939，约 300 秒，随后上传；没有新的故障注入或重连。
批次完整，窗口内至少 1,158 个采集事件被显式丢弃；8,169 是会话累计值，不是该窗口值。

| 离线策略 | 可用媒体帧 | PLC 帧 | 最长输出间隔 | 虚拟 PCM 欠载总时长 |
| --- | ---: | ---: | ---: | ---: |
| 现有跟踪，300ms | 54,436 | 5,134 | 304.95ms | 1.944s |
| 现有跟踪，600ms | 57,216 | 2,285 | 601.47ms | 1.989s |
| 候选跟踪，300ms | 59,272 | 124 | 68.58ms | 2.814s |

结论：候选值得开发，但不能只看 PLC 下降。它保留更多有效媒体，也把部分时间线等待
转换成输出供给空档；真实实现必须协调 PCM 储备、时钟恢复和重新同步。
把缓冲直接加到 600ms 会增加延迟与重填空档，优先级较低。
这些结果不是对当前实机 PLC 数或听感的预测，也不能证明所有失声成因已解决。

优先路线：

1. 保留现有 120ms 时间分集，先修复“仍有新数据却长期被截止期丢弃”的反馈路径。
2. 分离缓慢时钟漂移与突发媒体停顿，评估有界重新同步，避免 PLC 与无 PCM 供给互换。
3. 在后续开发版增加可区分网络接收与线程调度的时间戳/进度证据；不依赖固定 AWDL 相位。
4. 持续记录不同自然网络状态；现有样本不足以外推任意 iPad 网络。

## R4：持续的被动观察

本机已启用：

- `moonlight-diagnostics.service`：原有 HTTPS 日志接收，原有容量/时间保留限制不变。
- `moonlight-diagnostics-watch.timer`：每五分钟对至多两段最近会话生成摘要。
  每段最多读取最近 150 批并保留 300,000 个相关事件；摘要进程实测约 140MiB 峰值，
  限制 384MiB、25% CPU，退出即释放。
- `moonlight-diagnostics-host.service`：跟随已有发送日志，剔除 payload hash 等多余字段，
  保留发送尝试、序号、长度及副本调度延迟。它不能联网，不修改原日志或 Sunshine。
  只对自己生成的压缩元数据应用 128MiB / 至多七天限制；实际留存取决于数据率。

状态目录：`~/.local/state/moonlight-diagnostics/`。
`latest.json` 为最近一次有新数据的摘要，`health.json` 为最近检查时刻与上传新鲜度；
`host/` 为主机压缩元数据，`host-clock.json` 提供本机墙上/单调时钟关联。
没有新上传时，不猜测是后台挂起、结束串流还是断网。

通知按用户全局约定：启动已通知，普通监控摘要每天最多一次；观察到持续管线异常或
后台诊断任务退出时通知。通知不含媒体、输入、凭据或完整日志，配置位于用户私有目录。
关注两种迹象：视频继续但输出进度落后；真实包仍到达但十秒样本几乎全为 PLC。
**没有自动重连、改参、重启串流服务或操作其他应用的动作。**

停用这两项新增被动任务：

```sh
systemctl --user disable --now moonlight-diagnostics-watch.timer moonlight-diagnostics-host.service
```

## 复现与验证

```sh
python3 tools/diagnostics/diagnose.py SESSION --host-log HOST_SNAPSHOT.log \
  --capture-info capture-info.json --output paired.json
python3 tools/diagnostics/replay.py SESSION session.replay.txt
sh tools/diagnostics/build_replay.sh /private/path/replay
/private/path/replay session.replay.txt baseline 300
/private/path/replay session.replay.txt adaptive 300
python3 -m unittest discover -s tools/diagnostics -p 'test_*.py'
```

`diagnose.py` 的自动主机会话选择使用近似墙上时钟作筛选；匹配歧义时拒绝自动选择。
原始日志未区分多客户端流；多客户端同时串流时不能未经区分就合并归因。
当前 `--host-log` 接受原始 EV 文本快照，sidecar 的 JSONL gzip 保留供显式解包/关联。

18 项单元/协议/重放检查通过。实际新窗口的 C 重放另通过 ASan/UBSan；未修改实机代码，
因而本轮没有重新构建或替换 iOS 应用。候选时钟策略仅位于离线工具。
私有工作区的 `artifacts/natural-diagnostics-20261105/` 保存快照、参数冻结记录、摘要、
逐步重放结果和 `timing-evidence.png/pdf`；原始日志和私人配置不进 Git。

补充输出层观察：持续观察中，旧的显式重建测试之后，输出修复计数又从 1 增到 3。
控制台分别记录了音频路由变化及前台激活；两者会按设计请求重开，因此不能凭该计数
认定出现了自然失声或冻结播放设备。当前观察到的路径包括无线/截止期和 iOS 输出会话，
摘要报警不以“修复计数增加”作为故障条件。
本版路由/前台回调主要记录在控制台，二进制 trace 的 ROUTE 类型尚未完整覆盖；只有
上传 trace 时，不能以没有 ROUTE 事件断言没有路由变化。开发机也同时承担其他工作，
主机节奏差不能直接归因于无线，后续需要在不同自然负载下复核。

工具测试已分别在 Linux 与 macOS 通过，Mac 的长流、漂移及恢复回归也通过。
独立测试脚本补齐了 vendored ENet 的 include 路径，避免依赖 Linux 上恰好安装的系统头文件。
